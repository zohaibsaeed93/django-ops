WHAT THIS TEACHES YOU

“The container is up”
is only the beginning.

A running container can still have an unreachable database, unapplied migrations, or an absent worker.

DjangoOps asks Django-specific questions. Can the application connect to its database? Is its schema current? Do the workers respond?

Try a database or worker failure. The result points at the affected part of the stack, rather than giving you a generic red light.

WATCH THE MIGRATION GATE

A deployment is more
than a new image.

Failed migration? The release stops before activation. The existing application remains active.

New release unhealthy? Rollback is allowed only when database compatibility makes it safe.

Compatibility unknown? DjangoOps blocks automatic rollback and calls for operator recovery. It does not guess reverse migrations.

Start with a successful deployment. Then choose “Migration failure” and compare how far the release gets.

RECOVER WITHOUT GUESSING

Keep a recovery point
for the recovery itself.

Validate first. A corrupt or incomplete backup is rejected before writers are stopped.

Preserve current state. Keep a pre-restore database and media copy so an operator has another recovery option.

Stop writers, restore, verify. Restart the configured web and worker services, then check Django health.

Real PostgreSQL and media backup operations are provided by the direct SSH CLI. This page teaches that workflow through sample data.
